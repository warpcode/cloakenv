## 2026-11-08 - Capacity Preallocation in Search Pipelines
**Learning:** `SearchResult` structs in `cloakenv` are large (~96 bytes each), meaning uninitialized dynamic slices (`var results []SearchResult`) trigger repeated doubling reallocations and GC churn across large databases (e.g. 10k items cost ~4 MB in intermediate reallocations alone). Sizing slice capacity to candidate counts (`len(p.entries)` in static search or `len(allResults)` in `filterResultsByExpression`) eliminates this churn completely. However, blind preallocation is an anti-pattern when queries apply restrictive pre-filters (such as specific tag or path filters in `CustomVaultProvider`), where allocating `len(entities)` can allocate megabytes when zero or few items match.
**Action:** Preallocate search result slices when the query is unbounded/filtering occurs downstream (e.g., orchestrator `SearchQuery{}` and `filterResultsByExpression`), but avoid full-capacity preallocations on highly selective pre-filtered queries.

## 2026-11-07 - Pre-classified Key Dispatch in Search Result Flattening
**Learning:** In CLI result formatting (such as `flattenSearchResults`), repeated string lowercasing and 14-branch string switch statements inside loops over search results impose noticeable CPU overhead per entry. Classifying the selected key list once prior to the result loop into a small numeric enum allows the inner loop to use direct jump tables / integer comparisons without redundant string inspections.
**Action:** When transforming large sets of search or query results by a user-supplied field/key filter, pre-parse and classify the key filter upfront rather than evaluating strings inside the entry iteration.
